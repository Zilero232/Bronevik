# CLAUDE.md — apps/game/modpack

Guidance for the game-client modpack. Extends the root [../../../CLAUDE.md](../../../CLAUDE.md); those rules still apply. The full reference — layout, hooks, payloads, build, install — is [README.md](README.md).

**Python 2.7** packages the «Мир танков» client loads from `mods/<client version>/` as `.mtmod` (Lesta 1.35+; `.wotmod` for WG). It is a bun workspace (`@otmetki/modpack`: `test`, `lint`, `build` scripts) and a uv workspace (`pyproject.toml` + one per package) for the Python 3 host tooling. Its Python half is not part of `bun run verify`; `ui-web` (the in-game window's TypeScript and SCSS) is: typecheck, ESLint, Prettier, Stylelint (its own `ui-web/stylelint.config.mjs` adds the Gameface bans).

## Two kinds of code

| Where                                                 | What                                                     | Tested                 |
| ----------------------------------------------------- | -------------------------------------------------------- | ---------------------- |
| Any `*.py` outside `client/` and `entry/`; `model.py` | Pure logic, **Python 2/3 compatible**, no client imports | its package's `tests/` |
| `client/` folders, a feature's `client.py`, `entry/`  | Glue that imports `BigWorld` / `gui`                     | the import smoke only  |

Keep as much as possible in the pure half — it is the only half the checks can run.

## Rules

- **Python 2.7 syntax in the game sources.** No f-strings, annotations, `async`, walrus or `match`. Python-3-only modules (`urllib.request`, `pathlib`, `typing`, …) only inside a `try/except ImportError` fallback. `tools/tests/test_py27_compat.py` enforces both.
- **No load order.** The client imports `mod_*.pyc` in hash order. Never assume the core, the app or another feature is initialised first: features register through `core.registry` (`register()` in their entry script), and the app binds when it starts.
- **A feature is a folder:** `features/<id>/` with `__init__.py` (`FEATURE_ID`, `PACKAGE_ID`, `VERSION`, `create(app)`, `register()`), `entry/mod_otmetki_<id>.py`, and the packages `model/` (pure), `client/` (glue on `app.bus`), `settings/`, `i18n/`, plus `tests/`. `tools/tests/test_layout.py` checks the shape. Core and companion follow the same rule: one folder per concern, glue in its `client/` subfolder, constants in its `constants.py`.
- **Feature glue starts from core.** `FeatureComponent`, `BattlePanel`, `NativeSettingsComponent`, `Ticker`, `core.client.game` / `garage` helpers and `ReasonError` instead of per-feature copies; core guards every hook, so handlers carry no try/except of their own.
- **Libraries before custom code.** `packages/core/vendor` holds six, blinker, attrs and enum34 at pinned py2.7 versions with their licences; `python tools/vendor/vendor.py` rewrites it from the pinned wheels (`--check` verifies). Never edit vendored files by hand.
- **HUD panels take part in HUD edit mode** through `core.hud.HudPreview` (`hud_edit`, `hud_describe` on `app.bus`), with sample text from the feature's `model/preview.py`.
- **Every package has a catalog entry** in `catalog/catalog.json` (titles ru/en, category, presets, fair-play note, preview in `catalog/previews/`) and a bilingual `## <id> <version>` entry (`### ru`, `### en`) in `CHANGELOG.md`. `tools/build/setupkit/manifest/tests/test_manifest.py` and `tools/most/texts/tests/test_most_changelog.py` fail without them.
- **Settings stay in the companion schema** (`packages/companion/config/`) so `config.json` keeps a switch while its feature is not installed; a feature's `settings` lists the keys it reads. A battle HUD component's look and position live in its own schema-checked section of `components.json` (`core/hud`), its on/off switch in `config.json`.
- **The settings window is behind `SettingsView`** (`companion/settings_ui/client`). ModsList master needs WG 2.4.1+; do not make the app depend on ModsSettingsAPI. The Gameface window (`packages/ui`) is added next to it with `add_settings_view`; it renders every card from the feature's own schema, so a new feature needs no UI code: `settings.SETTINGS` (its config.json switch), `settings.SCHEMA` (its components.json section), optional `GROUP`, labels `component_<id>`, `<id>_<key>`, `<id>_<key>_<value>` in its i18n; buttons and list pages through `ui_actions()` / `ui_page()` / `ui_action()` on the feature instance (README «In-game UI»).
- **`ui-web` is feature-sliced** (`app`, `widgets`, `features`, `entities/window-state`, `shared`): entries are one line (`onDomReady` + `mountOnce`), components only render, hooks in `model/hooks`, constants in `config/`, the Gameface globals only behind `shared/api/gameface` (mock in `shared/api/gameface/mock`). No `ul`/`li`/`dl`/`select` elements or `radio`/`range`/`checkbox` inputs (Gameface polyfills or lacks them; ESLint, Stylelint and the bundle test enforce it); the settings page ships its script as a classic IIFE at the end of the body. After a change, `bun run ui:build` and commit `packages/ui/gameface` (README «In-game UI»).
- **Client settings only through the game's own options.** Components that change the player's client settings (`minimap`, `camera`, `crosshair`, `hangar_tweaks`) go through `core/client/native` with `native` meaning "leave the game's value", and write only on the player's change in the hangar. Anything beyond the game's own options (camera distance, free look, Flash patches) stays out until Lesta confirms it.
- **Hangar actions only on the player's request.** Components that send client requests (`hangar_tweaks` quick actions, `auto_resupply`) run them from a window button, never on their own; overrides of client views (`chat_filter`, `notification_filter`, `hangar_cleaner`) call the original unless their switch hides the element, and never touch the player's own lines or plain messages. README «Left out of the component catalogue» lists what stays out and why.
- **Fair play is a hard constraint.** Read only the player's own data; never read or show enemy positions, reload timers, aim or spotting data. Never serialise the `vehicles`, `players` or `avatars` blocks of battle results — `test_payload.BattleEventTest.test_never_leaks_other_players` enforces it.
- **Nothing is sent before the player binds the mod**, and every feature can be switched off in settings.
- **The contract is the API's contract.** A payload change updates `contract/*.json` and the server's ingest schema together; the server's tests read `contract/examples/ingest.example.json`.
- **Settings files a player cannot recreate go through `core.durable.open_config`** (credentials, config, components, profiles, state): it mirrors them into `%APPDATA%\TriOtmetki` because МОСТ may wipe `mods/configs`; the newer copy wins on load (README «Durable settings»). A new file of that kind joins `DURABLE_FILES`.
- **Release packages ship `.pyc`.** The production client loads only `mod_*.pyc`.

## Commands

```bash
bun run test:modpack                                         # stdlib runner over every tests/ folder
cd apps/game/modpack && uv sync && uv run pytest                  # the same tests under pytest
cd apps/game/modpack && uv run ruff check .                       # lint (E, F, W; pyupgrade off; core/vendor excluded)
python apps/game/modpack/tools/vendor/vendor.py --check           # core/vendor matches the pinned wheels (downloads them)
python apps/game/modpack/tools/build/build.py                     # dev build -> dist/*.mtmod, one per package
python apps/game/modpack/tools/build/build.py --single --require-pyc   # release, single package; needs a compiler
python apps/game/modpack/tools/build/build.py --dry-run           # list packages and in-game paths, write nothing
cd apps/game/modpack && bun run ui:build                          # rebuild packages/ui/gameface from ui-web with Vite (commit the result)
cd apps/game/modpack && bun run ui:dev                            # the settings window in a browser, with a mock Gameface bridge
cd apps/game/modpack && bun run ui:test                           # ui-web tests, Vitest project modpack-ui (also in the repo's `bun run test`)
cd apps/game/modpack && uv run python tools/build/setupkit --packages dist   # components.json + previews for the manager -> dist/catalog
cd apps/game/modpack && bun run most:bundle --game-version 1.45.0.0   # МОСТ submission bundle -> dist/most
```

The deploy workflow runs `test:modpack` on Python 3 ([.github/workflows/deploy.yml](../../../.github/workflows/deploy.yml)). [.github/workflows/modpack.yml](../../../.github/workflows/modpack.yml) runs pytest, the stdlib runner, ruff and vermin on Windows for pull requests, and a manual release build with `owg_python_compiler` that also uploads the component catalogue (`components.json` + previews) for the manager. Players install through the manager ([apps/game/manager](../manager/README.md)); there is no separate installer.
